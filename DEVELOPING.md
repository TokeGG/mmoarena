# Developing and hosting the game

Everything a player does not need: running the game locally, tests, the project rules, bot training, hosting on Render, the database, owner tools and security. The player guide is [README.md](README.md); the skill and talent reference is [WIKI.md](WIKI.md).

## Running locally and tests

```bash
npm install
npm run dev:server        # game server on :8080
npm run dev:client        # Vite on http://localhost:5173 (proxies /ws to :8080)
npm run build && npm start     # production: one process serves the client and WebSocket
npm test                  # simulation, bots, builds, replays, accounts, matchmaking, friends, tooltips, real WebSocket end-to-end
npm run typecheck
npm run duel              # headless bot-vs-bot win rates for every composition
npm run duel -- 30 hard   # 30 seeds per matchup, hard bots
npx tsx scripts/gen-wiki.ts    # rebuild WIKI.md from the data (a test fails while it is out of date)
npx tsx scripts/train-rotations.ts   # relearn every spec's damage rotation (seconds)
npx tsx scripts/train-bots.ts  # relearn the bot brains by self-play (minutes)
```

`npm run duel` measures how the bots' playbook performs, not how humans will. Use it to catch broken classes and wildly lopsided numbers, then tune `shared/data/*.json`.

## Project rules

The full list is in [CLAUDE.md](CLAUDE.md). In short:

- **Replays:** whenever simulation code (`shared/src/sim.ts` and anything it uses) or game data changes, bump `SIM_REVISION` in `shared/src/replay.ts`, otherwise older replays would play out differently. Replays are also gated by a hash of the data files, so a stale one says so instead of showing a wrong fight.
- **Versions:** bump the version in README line 1, the root `package.json` and `client/package.json` together (kept below 1.0), and add the matching entry at the top of `shared/data/patches.json` (the in-game Patch notes; a test checks the versions agree).
- **Bots:** a change to abilities, specs, talents, weapons or class mechanics also updates `shared/src/bot.ts` so bots use the new skills, and the per-spec bot test must pass. Then re-train (below) and commit `shared/data/rotations.json` and `shared/data/botbrain.json`.
- **Wiki:** after changing abilities, auras, specs, talents or tooltip wording, run `npx tsx scripts/gen-wiki.ts` and commit `WIKI.md`.

## Bots and learning

- Bots play from a tunable brain (cover and defensive thresholds, strafing, healer priority, focus fire, kiting range, heal timing, burst timing, chase, ground-zone dodging, pre-shielding).
- Bots take talents (a random pick in most tiers), so the tier IV trinket and the tier V class skills are played by bots too; a test checks that every ability on a bot's bar gets used.
- **Rotations:** `npx tsx scripts/train-rotations.ts` searches each spec's damage-ability order against a target dummy (the real cooldowns, costs, procs and combo points; several talent builds per spec) and keeps the order that deals the most damage, in `shared/data/rotations.json`. Bots press their filler in that order; finishers and rage dumps go off at their own thresholds, crowd control is spent on purpose.
- **Player tricks:** casters fake casts (start one and stop it) while an enemy's interrupt is ready and in reach; interrupters wait into a cast before kicking, longer against someone who has faked before; bots step behind pillars, walls or decks to make a long cast at them fail, take cover the same way when hurt (on the walk grid, both floors), take the ramp up to someone on a walkway, and keep sidestepping between casts. How much of each they do is part of the brain (`jukeChance`, `jukeAt`, `kickAt`, `losUse`, `mobility`), so it is trained and learned like the rest.
- **Difficulty:** Easy reacts in about 1.3 s, thinks less often, skips a third of its decisions, interrupts rarely and saves itself late; Normal is in between; Hard reacts in 0.16 s.
- `npx tsx scripts/train-bots.ts` runs bot-vs-bot self-play (a few minutes) in 1v1, 2v2 and 3v3 on every arena in turn, and writes the trained baseline to `shared/data/botbrain.json`. Brains stored by the server are completed from that baseline when they load, so a brain saved by an older version never misses the newer traits.
- Live, the server keeps six brain variants per class, hands one to every bot it spawns, credits each finished match against a human (20 s or longer, no draws) to that variant, and replaces the weakest with a mutation of the best. Variants are stored in the same Upstash store as accounts (memory only without it); `/api/status` shows them.
- After each recorded match the server replays it, measures what every human did (strafing, distance to target, health when using a defensive, healer focus, team focus) and keeps a running per-class human style; each class gets a "human" brain variant pulled towards that style, which only survives if it wins.
- **Learning from being outplayed:** the same replay is studied for how the people beat the bots (`shared/src/outplay.ts`): a bot's casts kicked while a kick was ready on it, the point in a cast people kick at, its own kicks juked by a fake, deaths with a long defensive still ready, deaths to an unanswered burst, long casts taken in the open, time spent in ground effects, a melee bot kited or a caster pinned. Each becomes a lesson for one brain number, counted three times over when the person won. Lessons only push the way they point (a bot that already defends earlier than a lesson asks is left alone). Each class gets a "lesson" variant (the best brain moved towards them, rebuilt after every replay), and new variants are bred towards the lessons, so the population improves in tens of games rather than hundreds. `/api/status` shows each class's real win rate against people by the person's class and the bot's difficulty.
- **What the bots learn, in full (`shared/src/mistakes.ts`, `shared/src/learnreport.ts`):** besides the eight mistakes above, a replay is watched tick by tick for thirteen more, each with its own brain number and a hook in `shared/src/bot.ts`. *Locked down* (stun, fear, sheep) for 1.5 s with the cleanse trinket ready, or *dying with the trinket ready*, teaches `trinketAt` (how soon it uses the trinket: the cleanse delay and the health the heal trinket fires at). *Dying with an offensive cooldown ready* teaches `burstUse` (the health below which it pops Recklessness, Adrenaline Rush, Arcane Power... whatever the target). A caster *standing still with melee on it and a push-off ready* teaches `peelAt` (how early Frost Nova, Psychic Scream and the rest are used). For healers: an ally dying with the shield or Pain Suppression ready teaches `shieldAt` (and `healAt`), an ally under 40% with the healer idle teaches `healAt`, and heals mostly wasted on full-health allies teach `healCap` (down). *Dropping a target under 30%* teaches `switchHp` (finish it instead), *three seconds on a target it could not hit* (out of sight, invulnerable) teaches `stickiness` (down: it leaves such a target sooner, and any target scores less for having been picked). Casts failing for no line of sight or range teach `losCheck` (how fast a cast at a vanished target is stopped) and `rangeBuffer` (yards kept inside the maximum range). Crowd control thrown at a target already at 25% or less teaches `drRespect`. Being out of mana in a fight teaches `spendBias` (Evocation sooner, no filler spells on an empty bar). Not measured, and why: using high ground when kited (no clean yes/no from a replay), staying near the healer (a team-movement question with no single mistake to count), crowd control on the wrong target (the replay cannot say which was right) and chains that overlap (the sim already refuses most of it). Every lesson has a direction and a magnitude: its value is the default moved towards an extreme by `1 - exp(-count/3)`, its weight is count times 20 (times 1.5 for a loss, 0.5 for a win), and `lessonBrain` takes a step of up to 80% of the way in proportion to the evidence. Evidence adds up across replays per class (older evidence fades by 8% with each new lesson for the same number), one replay moves a number at most a fifth of its range (times the passes, up to three), and nothing ends up further than 60% of its range from the shipped brain. New numbers are added to `Brain` with bounds and defaults in `shared/src/botbrain.ts`, so an older `botbrain.json` still loads (missing numbers read as the defaults).
- **Every fight teaches something (graded signals, `shared/src/graded.ts`):** besides the countable mistakes, each bot's fight is measured as rates and compared with the person who fought it, measured the same way: standing still, time in an enemy's sight, line-of-sight breaks a minute, sidestepping, distance to its target, time out of its healer's reach, seconds in lava, burst cooldowns idle while the enemy was in reach, the health it pressed defensives at, target changes a minute, the health it used the trinket at. Every difference above a small floor becomes a nudge (`gradedNudges`): the numbers it points at (`mobility`/`strafe`, `coverHp`/`losUse`, `rangeBias` or `chase`, `stayNear`, `edgeCare`, `burstUse`/`burstHp`, `defHp`/`panicHp`, `stickiness`/`switchHp`, `trinketAt`) move a small step (4% of the range at full strength, half for a win, times the passes) towards how the person played. The server adds the nudges up per class on top of the lessons. A number at its limit from the shipped brain gets 10% more room (to 95%), a number at its hard bound passes the nudge to the next number on its list, and the report says which. The movement numbers: `stayNear` (turn back to the healer partner when further than `44 - 24 * stayNear` yards, or out of sight above 0.5; off at 0) and `edgeCare` (no hop for its own sake within `2 + 6 * edgeCare` yards of a lava pit), next to the existing `mobility`, `strafe`, `rangeBias`, `chase`, `coverHp`, `losUse` and `dodge`. A fight is only reported as teaching nothing when it was too short (under 8 s), no bot fought a person, or the bots played it exactly as the people did.
- **What the owner sees:** every training run (one replay, N passes on one replay, every archived replay, or the automatic path after each match) produces a `LearnReport`: the mistakes found per bot by type with counts, the brain numbers that moved per class (`mage: peelAt 0.50 -> 0.58`), or an honest "Nothing to learn from this match: <reason>" (too short, bots won and no mistakes, mistakes too few to teach yet, bots already at or past the lesson, no bot fought a person). It is shown as an expandable line under each queue row in the admin panel's Replays tab, kept in the store (`botreports`, the last 50) and listed under *What the bots know*, which also shows per class the learned numbers against the shipped ones, how many replays taught the class, when it last learned and how the learned variant is doing. Buttons: *Train on all archived replays* (skips and counts replays from another version of the game), a passes selector (1..5) for the owner's forced training, and *Reset learned brain to shipped defaults* (asks to confirm). The learned brain joins the class as the "lesson" variant and plays in a share of its games until it wins its way up. `scripts/study-replays.ts` prints the same report.
- **Offline, from real replays:** the server keeps the newest 400 matches between people and bots (solo practice included, 30 days each). `npx tsx scripts/study-replays.ts --server https://your.server --code OWNER_CODE` (or `--store` with the Upstash variables, or `--dir` with replay files) plays them back, prints how each bot class is being beaten and its real win rates, and writes `shared/data/players.json`; `--apply` also moves `shared/data/botbrain.json` towards the lessons. `scripts/train-bots.ts` then trains against opponents that play like people of their class (spacing, sidestepping, kick timing, fakes), weighted towards the match-ups bots lose most to people, and `npx tsx scripts/train-bots.ts --calibrate` lists its simulated 1v1 win rates next to the real ones. Only replays recorded on the current game data can be played back, so study after a patch has had some games.

## Netcode (Stages 1 and 2, see NETCODE.md)

The sim runs at any tick length (`tickMs`, whole milliseconds): 50 ms (20 Hz) is the default in the code and in tests, the production blueprint sets 16 ms (62.5 Hz). The pipeline around it (protocol 10):

- **Tick length (Stage 2).** `SimOptions.tickMs` (default `TUNING.tickMs` = 50) is the length of one `ArenaSim.step()`; every rule runs on sim time in milliseconds, so a match plays the same at any value (casts, stuns, channels and DoTs end at the first tick at or after their time, i.e. within one tick). The input queue limits, the repeat-last-input window, the catch-up depth and the lag-compensation history are written in milliseconds (`INPUT_QUEUE_MS` 250, `INPUT_REPEAT_MS` 150, `CATCHUP_*`, `HISTORY_MS` 600 in `sim.ts`; `sim.limits` has the tick counts, identical to the old 5/3/2/2/5/12 at 50 ms). Bots think on a clock in ms (`Bot.afterThink`, 50/100/300 ms). A replay records its `tickMs` (only when it differs from `TUNING.tickMs`) and `contentHash(tickMs)` includes it, so a replay recorded at 16 ms plays on 16 ms steps whatever the server runs now. At 50 ms every outcome is identical to before the change (`shared/test/tickms.test.ts` holds digests of full bot matches captured from the old code).
- **Server setting.** `ARENA_TICK_MS` (whole number 8 to 50, default 50, anything else is refused with a warning and 50 is used) is read at start-up (`parseTickMs` in `server/src/index.ts`), logged, applied to every new room (`LobbyConfig.tickMs`), sent to clients in `welcome.tickMs`, and shown in `/api/status` (`tick.ms`). The rate limiter allows `max(120, 2000 / tickMs + 60)` messages per second per socket (185 at 16 ms). Room cadences (spectator delay 5 s, end screen 300 s, stats every 500 ms, paused frames every 250 ms) are in ms via `Room.ticksIn`.
- **Server load meter.** `server/src/tickmeter.ts` records how long each tick of all rooms takes (per-second buckets): `/api/status` has `tick: { ms, avgMs, maxMs, load, late, worstMs, rooms }` (`load` = average tick cost / tick length over 10 s; `late` = ticks in the last minute that took longer than a step or started more than one step late); the admin panel's dashboard shows it (red above 70 % load or with late ticks) and the console logs one `server busy` warning (at most a minute apart) when the load stays above 70 % for 10 s. It never changes the tick length by itself. Clients see `load` in `pong` and the network readout says `server busy` above 90 %.
- **Testing at 16 ms.** `npm run test:16` runs the whole suite with `TUNING.tickMs` set to 16 in memory (`scripts/tick-preload.mjs`, `TICKMS=8 ...` for another value); tests that count ticks use `sim.tickMs` or ask for 50 ms explicitly. `shared/test/tickms.test.ts` covers tick independence at 50 and 16 explicitly.
- **Pairwise agreement.** `npx tsx scripts/netstudy.ts --target` measures how far apart two screens draw the same player (see NETCODE.md section 10); the client's `Lead` (dead reckoning of other players by 0.75 x round trip, at most 150 ms) comes from it.
- **Pause and map swap.** While a dev test match is paused the client draws exactly the last snapshot (no extrapolation, no prediction, nothing sent) and `estimatedNow()` is the frozen server time; on resume, a restart (`dev_state.reset`) and a map swap `resetNetState()` throws away the buffer, the clock, the delay statistics, the prediction and the camera anchor. The server drops queued inputs on pause/restart/swap and sends the next paused frame at once.

- **Ping/pong.** The client sends `ping { n }` every 2 s, the server answers `pong { n }` at once from `Lobby.handle` (any state). `NetStats` (`client/src/netStats.ts`) turns it into ping and jitter (smoothed round trip, RFC 6298 style), loss (gaps in `snap.tick`), tick spacing and the view delay. The corner readout is the Esc-menu setting "Show network stats" (`arena.netstats`, off by default) and is always on for devs. `/api/status` has `tick: { rooms, avgMs, maxMs }`, the server's cost of a whole tick.
- **Clock.** `client/src/netClock.ts` (`NetClock`): `offset = serverTime - localTime` per snapshot, the largest over a 2 s window (the fastest packet), slewed 10 % per snapshot, `now()` never decreases. Used for render time, cooldown/GCD checks and `vt`. `RttEstimator` is in the same file. Pure, tested in `client/test/netClock.test.ts`.
- **Interpolation delay.** `client/src/interpDelay.ts`: `targetDelay = clamp(max(1.5 x interval, interval + p95 lateness + 10 ms), 24, 200)`, eased (up 20 %, down 2 % per snapshot); `RenderTime` = clock - delay, never earlier than the last frame; `poseAt` extrapolates past the newest snapshot for at most 100 ms with the velocity fading to zero (no extrapolation over a teleport, and never for spectators/replays). The `vt` sent with casts is the render time of the last drawn frame, so the server's lag compensation (`maxRewindMs`) matches what the player saw.
- **Own character.** `client/src/ownAhead.ts`: drawn at `pred + (pred - prevPred) * acc / DT`, i.e. the last predicted step carried on by the time since it was taken (not blended up to a tick behind). Reconciliation is unchanged (snap `pred` to the server position and replay `pending`; the 38/s easing hides the correction, a jump above 4 u teleports). Range checks use the caster's server position as before; drawing ahead raises the client/server distance mismatch a little (study: p95 0.13 -> 0.44 u).
- **Input catch-up (sim change, `SIM_REVISION` 90).** `tickUnit` in `shared/src/sim.ts`: when more than `CATCHUP_DEPTH` (2) inputs are queued, surplus inputs are consumed in the same tick, but only as many as the clock has run: a tick that repeated the last input (`owed`) is matched by consuming one queued input *without* moving (the unit already moved), and a tick where the unit stood still with nothing to play (`catchUp` credit, max 5) lets up to `CATCHUP_MAX` (2) queued inputs move it per tick. A client therefore can never move more ticks than have passed, however many inputs it sends (the queue cap of 5 and the 120 messages/s socket limit stay). Replays record inputs as received, and the catch-up is part of the sim, so replays of `SIM_REVISION` 89 or older are refused by `contentHash` as for any rules change.
- **Server loop.** `startTickLoop` (`server/src/index.ts`): `setInterval(1)` plus a `performance.now()` accumulator with a fixed step of `tickMs` (`ARENA_TICK_MS`), at most 150 ms worth of ticks per callback (at least 3), the rest of a backlog dropped. Tests call `lobby.tick()` directly.
- **Snapshot diet.** `shared/src/snapslim.ts`: a team's `SlimEncoder` sends each unit's identity (name, team, class, spec, look, bar, trinket, stealth swaps, resource type) once as `info` (and again if it changes); per tick only the changing state. A player's first frame carries every identity. The client's `SnapMerger` rebuilds full `UnitSnap`s in one place (`onMessage`), and passes full units through unchanged (spectators, paused frames, replays). The spectator feed and the stored 100-tick history are still full snapshots (late watchers need them).
- **Study.** `npx tsx scripts/netstudy.ts --only stage1` (seconds) compares the old pipeline with Stage 1 using the real client modules and the real sim; `--quick --only net` runs the whole net section. See NETCODE.md section 8.

## Character models

Every class wears a skinned model; the procedural primitives (`createCharacter` in `models.ts`) are the fallback while a model loads or if it fails to load, and what `?warriormodel=procedural` forces. Warrior: the gold/black horned `knight` (default, every spec) and an optional `brute` with its own axe, previewed with `?warriormodel=brute` or `localStorage['arena.model.warrior'] = 'brute'` (it is only fetched when picked). Mage: the animated Old Wizard (`wizard`). Rogue: the Hooded Shadow Assassin (`assassin`). Priest: the Abyssal Sentinel (`sentinel`). A `ModelDef` names its file by a `.glb` url, but only the packed `.pak` next to it is served and fetched (see Packed models below), so a path such as `client/public/models/warrior.glb` below means `warrior.pak` in the repo. Scenes rebuild their characters when a model finishes loading.

**The owner must have the right to use every model that is committed (licence and credit them); never commit the original multi-megabyte source file, keep it outside the repo.**

Two scripts produce a game GLB (feet at y = 0, about 2.1-2.25 units tall, facing +z, character's left on +x), both configured by a JSON next to them in `scripts/models/`; coordinates in the configs are fractions of the model's height:

- `node scripts/rig-model.mjs <static.glb> scripts/models/warrior.rig.json client/public/models/warrior.glb [--debug <prefix>] [--cache <file>]` for an UNRIGGED mesh (e.g. AI generated, hundreds of thousands of triangles). It decimates (meshoptimizer) to `targetTris`, builds new UVs and bakes the original texture into a `textureSize` JPEG (the source atlas is too fragmented to survive decimation), splits the triangles into the cosmetic parts `head` / `shoulders` / `back` / `body` by `regions`, builds the standard skeleton from `joints`, and computes smooth skin weights (nearest bone capsule, blurred over the surface; `cloth` boxes make hanging cloth follow the thighs only partly so it does not tear). `--debug` writes `<prefix>.parts.glb` and `<prefix>.weights.glb` (vertex colours) to tune regions and joints by eye; `--cache` skips the slow decimate and bake step between runs.
- `node scripts/convert-skinned.mjs <model.fbx> scripts/models/warrior-brute.rig.json client/public/models/warrior-brute.glb --assets <texture dir>` for a model that is ALREADY skinned: keeps its weights, renames bones to the standard names (`bones`, `extraBones`), splits parts by `regions`, embeds the textures listed under `materials` (`texture`, optional `emissive` glow map).

Config fields: `height` (output size), `joints` (rig-model only), `regions` (`{part, box|ellipsoid}`, first match wins; `back` may be absent), `cloth`, `attach` (hand grip points, `attach_hand_l/r`), `runtime` (headCenter, headR, shoulderJoint, chestBackZ, torsoW, deadY: measured on the model, they place the cosmetics and the bare head and shoulder joints shown where an item replaces a part), `runtimeRaw`. The pose is procedural (`client/src/riggedPose.ts`, driven by bone rotations from the same inputs the procedural models use), so no clips are needed.

To add a model for another class or spec: run the script, put the GLB in `client/public/models/`, add a `ModelDef` to `MODELS` in `client/src/riggedModels.ts` and point `CLASS_MODEL` at it (`default`, `byWeapon` for a per-spec model, `alternatives` for preview choices; `pose` tunes the gait, `ownWeapon` skips attaching the spec weapons). Class-specific weapon building lives in `models.ts` (`warriorWeapons`), so another class needs its own held-item function the same way. Run `npx tsx --test client/test/models.test.ts` (it loads the GLBs from disk).

**Models with their own clips (the mage's Old Wizard):** a GLB that is already rigged AND animated is prepared with `node scripts/prep-character.mjs <file.glb> scripts/models/mage.json` (keeps the skeleton hierarchy, skin and every clip; drops the meshes under `dropMeshes`, downscales textures, scales to `height` facing +z, writes the credit and the rig metadata `rig.*` incl. `rig.bones` and `rig.hold` into the root node's extras). Its `ModelDef` sets `clips` (tuning, see `client/src/riggedClips.ts`: a THREE.AnimationMixer per unit, idle / walk / run blended by speed, the attack clip as the cast and swing, the death clip held then the body topples) `posture` (a standing correction for stooped clips: radians on the spine, chest, neck and head turned after the mixer every frame, fading out in a cast, in a run (`run` is the share kept) and in the fall; the Old Wizard's idle leans back with the head thrown up, so he gets chest 0.2, neck 0.22, head 0.08) and `dye` (the sub-meshes armor dyes tint). A clip model that stands beside its origin is moved onto it by `instantiateClips` (the wizard's hips were 0.17 to the left, so the cape, wings and aim were off to one side). Fit his wings with the harness trick of changing `MODELS.wizard.wings` between renders (his cloaks are not a cape mesh, see Capes). The spec staffs (`scripts/prep-weapon.mjs` presets `staff-*`, with `decimate`) are registered in `weaponModels.ts` with a `look` (robe tint through the dye shader, trim glow, motes at the staff head) and come from `specs.json` `weapon.id`. Run `npx tsx scripts/pack-models.ts` afterwards.

**Capes (back cosmetics with style `cloak`, `starcloak`, `embercloak`):** one shared skinned cloth, `client/public/models/cape.glb`, made by `node scripts/prep-cape.mjs <downloaded cape.glb>` (keeps only the five 11-bone cloth chains, neutral 512 px shading texture, credit in `asset.extras`; run `npx tsx scripts/pack-models.ts` after). `client/src/capeModels.ts` loads it with the other models (`capeModelVersion()` is part of `modelVersion()`), paints a canvas skin per item id (`capeSkinFor`: gradient, lining, trim along the hem / collar / sides, emblem, glow map; add an entry to `CLOAK_LOOK` for a new cloak, a new `style` needs a case in `capeSkinFor` and `CAPE_STYLES`), and moves the 50 chain bones as damped springs from the wearer's speed, strafing, turning and acceleration (`CapeRig.update`, driven from `Character.pose`). Fit per model: rigged models list overrides in `ModelDef.cape` (`riggedModels.ts`, defaults come from the rig metadata), procedural classes in `FIT[class].cape` (`models.ts`): `y`/`z` the collar in the torso frame, `sx`/`sy`/`sz` the cloth scale, `tilt`, `minPitch`, `worldDown`. Ribbons hang from the same collar point; the banner is separate. **A model whose robe already is a cloak** lists its sub-meshes in `ModelDef.robeBack` (and `robeFront: -1` when its file faces -z): the mage's Old Wizard wears no cape mesh, a cloak item (`cloak_*`, `starfall_cloak`, `ember_cloak`) recolours the BACK HALF of his own robe, hood and hem train included (`client/src/robeBack.ts`). Per vertex, once per shared geometry, `aBack = (mask, along)` is baked from the rest pose (mask 1 behind the robe's mid-plane, measured per height, easing to 0 over ~2 units either side; sleeves, found from the arm-bone skin weights, stay; `along` 0 at the collar to 1 at the hem), so the region follows every animation. The fragment shader is spliced into the dye shader (`robeShader` in `models.ts`): it keeps the robe texture's brightness and replaces its hue by the cloak's collar-to-hem gradient (colours from `capeSkinFor`, so they match the cloth other classes wear), a hem trim, and a procedural pattern from the rest position (starfall: twinkling white stars, ember cloak: orange specks and a glowing hem, snow: frost glints). **Dye rule:** the dye (and the spec's own robe tint) keeps the front half; the back half is always the cloak. Wings, ribbons and the banner are unchanged. `ModelDef.cape` of the wizard only places ribbons and the rift now. Wings are their own slot (below).

**Wings (the `wings` slot; there is no shoulders slot any more, the body's own shoulder parts stay):** one shared skinned pair, `client/public/models/wings.glb`, made by `node scripts/prep-wings.mjs <downloaded angel_wings.glb>` (turns the static feather-card mesh upright and centres it on the shoulder joint, adds the 7-bone skeleton `wing_root` > `wing_L` > `wing_L_m` > `wing_L_t` and the mirror `wing_R*`, a neutral 512 px grey texture with the feather cut-out in its alpha, credit in `asset.extras`; run `npx tsx scripts/pack-models.ts` after, the plain GLB goes to git-ignored `assets-src/models`). `client/src/wingModels.ts` loads it with the other models (`wingModelVersion()` is part of `modelVersion()`), and every item is that pair restyled by a `WingStyle`.

*Adding a wing style:* (1) add an item to `shared/data/cosmetics.json` in slot `wings` with a `style`, a `color`, a one-line `desc` (the tooltip) and its tier (no `unlock` = free, `unlock` = matches played, `owner: true` = founder only; owner items come last in the slot, the item's index in the slot feeds the compact gear string, so only append). (2) Without more work the item gets a plain look from its colour. For its own look add a row to `STYLE_ROWS` in `wingModels.ts` keyed by that `style`: `ramp` (shadow, body, highlight colours of the gradient map over the feather shading), `root` / `tip` (colour multiplied in at the shoulder and the feather tips), `glowColor` / `glowEdge` / `glowFill` / `glow` (the glowing outline of every feather and how bright), `size`, `raise`, `open` (the resting lift and sweep back, radians), `flutter`, optionally `layer` (a second tier behind the first: scale, raise, open, other ramp), `cycle` (hue cycling), `disc` (`ring`, `rays` or `eclipse` behind the wings) and `fx` (particles: `feathers`, `embers`, `frost`, `wisps`, `bolts`, `petals`, `stars`, `motes`, with colours, count and size; a new kind needs a case in the `Particles` class and a shape in its fragment shader). (3) Look at it: `wingStyleFor` is pure data, a test checks that every item has a style, a different look and works on every class. The wings flutter at rest, sweep back and lift when the wearer runs, beat when airborne, flare when it casts and fold when it dies (`WingRig.update`, driven from `Character.pose`); the particles stay where they were shed so a runner leaves them behind.

*Fit:* rigged models list overrides in `ModelDef.wings` (`riggedModels.ts`, defaults come from the rig metadata: the shoulder joint's height, just behind the back plate), procedural classes in `FIT[class].wings` (`models.ts`): `y` / `z` the shoulder joint in the torso frame (the wings sit further back than a cape's collar so both can be worn), `scale` the wing size, `sx` a stretch across for broad shoulders, `tilt`, `raise`, `open`. Old saves: `currentGear` / `cleanGear` (`shared/src/build.ts`) move wings saved in the back or head slot to the wings slot and drop the retired shoulder items.

**The rogue's Hooded Shadow Assassin** is an unrigged USDZ (781k triangles): convert it to a static single-primitive GLB first (`usd-core` in Python: read every mesh, apply the world transform, flip V, write one primitive plus the base-colour JPEG), then `node scripts/rig-model.mjs <static.glb> scripts/models/rogue.rig.json client/public/models/rogue.glb`. The config uses `centerX` / `centerZ` (raw source units; the body is not centred in the bounding box) and `textureGain` / `textureGamma` (the source is near black; the bake is brightened so dyes and cosmetics read, luminance detail kept). Its `ModelDef` (`assassin`) keeps the hood under head cosmetics (`keepHead`). The dagger (`scripts/prep-weapon.mjs dagger`) is registered as weapon `daggers` for all three rogue specs and held in both hands (the off hand mirrored). Run `npx tsx scripts/pack-models.ts` afterwards.

**Two-handed holds (`ArmHold` in `riggedPose.ts`, `WEAPONS` in `weaponModels.ts`):** `hold` is the two-handed pose (right and left arm pitch/roll/elbow; `arc` and `elbowArc` say how much of a swing's arc both arms follow; `elbowArc: 0` keeps both fists rigid on the weapon). A weapon with `hold.rest` plus `WeaponDef.rest` (pivot rotation in the right hand) is carried one-handed (the greatsword on the shoulder, the left arm swings free) and `RigAnimator.grip` (0..1) blends to the two-handed pose when a swing or cast starts and back 1.2 s (`rest.grace`) after the last one; `models.ts` applies it to the weapon pivot (`AttachedWeapon.setGrip`). To tune: solve the arm angles so the fists land on the wanted points and turn the pivot to the wanted direction (the numbers in `WEAPONS` came from such a solve; `client/test/weaponModels.test.ts` checks the left fist stays on the handle). The knight's rig config has `splitArms` (height): triangles joining forearm / hand vertices to hip, thigh or spine vertices are dropped, the weight blur does not cross that seam and small hip-weighted islands next to an arm follow the forearm, so the arms can rise without dragging the coat into shards (`scripts/rig-model.mjs`, `scripts/lib/skin.mjs`).

**The priest's Abyssal Sentinel** is an unrigged USDZ (1.1M triangles, 6 chunks of one mesh): convert it like the assassin (static single-primitive GLB with `usd-core` in Python), then remove what must not be in the body: the floating halo frame above the head, the sigil beside the left hand and the spars behind the head (the connected pieces whose top is above the helm, plus a few boxes around the head and the hand; the cut is a throw-away script, the result is checked in a front/side/back splat). Then `node scripts/rig-model.mjs <static.glb> scripts/models/priest.rig.json client/public/models/priest.glb`. The model is off-centre (`centerX` / `centerZ`) and stands with its forearms forward, so the joints sit where the arms really are; `textureGain` / `textureGamma` / `textureDesat` brighten and partly desaturate the bake (the gold and brown source would otherwise tint every dye); `splitLegs` drops triangles that join the two legs (the boots touch and tear apart in a stride) and `cloth` boxes keep the side flares and the back cloak on the hips. Its `ModelDef` (`sentinel`) keeps the helm under head cosmetics, gives a slow stride, holds the staff up less in a cast (`castR`, `castL`) and winds up less for a swing (`swingArc`). The staffs: `node scripts/prep-weapon.mjs staff-holy <holy_staff.glb>` (untextured, recoloured per material in the preset) and `staff-necro <necro_staff.glb>` (`mergeByMaterial` joins the five source chunks before decimating), registered as weapons `holy_staff` (Warden and Lightbearer) and `necro_staff` (Gloomweaver) and held like the mage staffs: the shaft stands up through the fist, no sideways offset. Run `npx tsx scripts/pack-models.ts` afterwards.

## Mouse cursors

`client/src/cursorArt.ts` draws every cursor as inline SVG on a 32 x 32 grid (no image files): the steel gauntlet (default, plus a pressing-finger link state over buttons) and ten more styles, each one drawing only its own normal art, and the three fixed override cursors every style shares (red sword, green cross, crosshair; the crosshair is one art in green or red); `cursors.ts` holds the rules and the page manager; `cursorUi.ts` is the settings panel (Esc menu and Profile > Customize). The styles and their unlock rules are `CURSORS` in `shared/src/accounts.ts` (same `Unlock` rules as titles and icons; the owner has all; a local cosmetic, never checked by the server). Settings are `arena.cursor.style|size|tint|ripple|trail|trailLen`, so they sync with the account; a locked or unknown style falls back to the gauntlet on load without erasing the saved choice.

- **Still styles** (gauntlet, wand, dagger, pixel arrow, ring, crown) are the native CSS cursor: `cursor:url(data:svg) hx hy, kw` plus `-webkit-image-set` / `image-set` 1x/2x forms, written into one `<style id="arena-cursor-style">`. `html.ac-pt` (set while the pointer is over something that declares `cursor:pointer`) swaps in the link art; text boxes and resize grips keep their own cursor.
- **Animated styles** (Ember, Frost shard, Void eye, Dragon claw, Starfall) and the optional ripple and trail use one overlay (`#arena-cursor-art` plus a click-through canvas) driven by a single `requestAnimationFrame` loop that only runs while something moves; `html.ac-own` hides the OS cursor only while the overlay is drawn. The overlay hides itself under pointer lock and while the right button steers (`input.ts`), and `prefers-reduced-motion` or a touch-only device falls back to the still art (or nothing).
- **Context** (`decideContext`, tested): `main.ts` gives `initCursors` a `situation()` (in a match, spectating, aiming a ground spell and whether it can land) and a `pick(x, y)` (the same `scene.pick` raycast as clicking, throttled to 60 ms while the pointer moves over the scene). The contexts are `default` (your chosen style; also menus, HUD, spectators, yourself, the dead), `enemy` (red sword), `ally` (green cross), `aim` (crosshair) and `aimBlocked` (the same crosshair in red when the spell cannot be cast or has no line of sight). Aiming beats hovering. The sword, cross and crosshair override the style and ignore the tint and glow; the animated overlay steps aside while one is active and the native cursor shows it.
- To add a style: an entry in `CURSORS` (unlock rule), a drawing and hotspot in `STYLE_ART` (`cursorArt.ts`, add `overlay: true` and CSS hooks in `cursors.ts` if it animates), then check it on a throwaway page that draws `cursorArt(style, state)` at 1x and 3x on dark and light; `client/test/cursors.test.ts` checks every style and state is well-formed XML within 128 px with its hotspot inside.

## HUD

`client/src/hudLayout.ts` is the HUD editor (Esc menu, Edit HUD): every element listed in `TARGETS` (by DOM id) gets a saved offset, scale and optional width/height (`arena.hud.v1`, fractions of the screen, sanitised by `parseLayout`), drag, corner grip, wheel scale, snapping and the **Reset all** button, which also resets the look options. `client/src/hudLook.ts` holds the look options (`arena.hud.look.v1`, one `data-hud-*` attribute each on the body, all enum choices so a stored value that is not on the list falls back to its default); both keys are `arena.*`, so they sync with the account. The **error text** (`#err`, shown by `Hud.error`: out of range, no line of sight, not enough mana...) and the **stun / control text** (`#ccstate`, one block with the aura name and its timer; the screen-edge glow `#ccvig` is separate and fixed) are ordinary `TARGETS` entries (`err`, `ccstate`) and have their own look groups ("Error text", "Stun text": size, colour, weight, outline, background, error duration 0.8 - 3 s, pop / fade, repeat suppression, stun pulse) shown with a live preview in the editor. `client/src/hudText.ts` is the pure part (CSS variables from the options, colours, duration clamp, `ErrorGate` for the 300 ms repeat rule), tested in `client/test/hudText.test.ts`. Both elements are empty most of the time, so in edit mode the stylesheet shows a sample ("Out of range", "Stunned 2.1s") through `::before`; code that changes their text must not use `className =` on `#ccstate` (the editor keeps its own classes there). Neither takes mouse clicks outside edit mode, and the whole HUD is hidden in menus and when spectating.

- **Leaving the editor:** Esc always leaves it (`escHandler` in `hudLayout.ts`, a capture-phase listener that also fires with focus in a drop-down, which the game's own key handler ignores); the open / close state (`hudEditState.ts`, tested) says whether the editor came from the main menu (the menu comes back unless a match started), `stop()` is idempotent and clears the `hud-edit` / `hud-demo` classes, selection, grips and focus, and the bar has **Done (Esc)**.
- **Network stats and the corner buttons:** the network readout (`#netstats`, `NetStatsView`), the sound button (`#mute-btn`) and the dev button (`#devbtn`, an icon above the sound button) are ordinary `TARGETS` entries, so they move, resize, reset and sync with the rest (`arena.hud.v1`); the readout sits bottom right above the help text by default, takes no clicks outside edit mode, and has its own look group ("Network stats": size, colour, background) in `hudLook.ts`; a button dragged in the editor is not also clicked.

## Skill visuals

Every ability is drawn from data: `ABILITY_VISUAL` in `client/src/skillVisuals.ts` gives it a class (projectile, onTarget, burst, aura, melee, movement, support, zone, channel); `client/src/effects.ts` draws it from the sim events (`cast`, `cast_start`, `damage`, `aura`, `leap_land` ...) and `AURA_VISUAL` gives lasting auras their layer. Nothing visual feeds back into the sim. Effects scale with the real numbers in `abilities.json` (`radius`, `coneDeg`, durations) and use pooled sprites (cap `PARTICLE_CAP`), shared geometries and materials, and no per-frame allocation.

Generic effects a data row or a `case` can pick (all in `effects.ts`):

- `fireCone(unit, range, half, dur)`: a true cone of flame (Dragon's Breath, Dragon Roar). Flipbook flame sprites (`client/public/fx/fire-sheet.webp`, 5 x 5 frames, drawn additively, per-sprite frame phase and speed; without the file the canvas teardrop is used), a white-hot core, dark smoke, embers, a flickering glow at the mouth and a ground `sector` that shows the real area. Flames spawn inside `coneSpawnAngle(u, half)` (`skillVisuals.ts`, tested), so the fire never leaves the cone the sim hits (`coneShape(def)` = `radius` yards, `coneDeg` wide).
- `soundWaves(unit, radius, color)`: pressure shells (open spherical caps with a rippled rim) leaving the face along the facing and growing to the real radius, plus a head-height ripple. `shockwave(x, z, radius)`: ground rings and ringed dust. `shout(...)` = body pose + the two above at the moment of release.
- `spinBlades(unit, radius, color, dur, turns)`: blades whirling round the caster (Cleave, Bladestorm, Slice and Dice).
- Flipbook fireball (`fireballFx.ts` + `fireballFlight` / `fireballWindup` / `fireballImpact` in `effects.ts`): the look of Fireball and Pyroblast, picked by a data row, `proj: { look: 'fireball', size, heat }` in `ABILITY_VISUAL` (`fireball(1, 0)`, `fireball(1.7, 1)`); every other projectile keeps the generic bolt. `fireballShape(size, heat)` (`skillVisuals.ts`, tested) gives every radius, count and rate. The `FireballRig` moves pooled sprites in readable layers, back to front: two glow halos, a dark red body (normal blending, so the fire has a darker edge), three large flame tongues of different sizes and rates that lick round the ball with their tips turned away from it and back along the flight (tip angles come from `effects.camera`, set in `main.ts`), a few small licks, a yellow-white flame body, a small white-hot core, and a soft light on the ground. The tail is a continuous tapered ribbon (a camera-facing strip with vertex colours and alpha: orange to red to dark to nothing, plus a longer dark smoke ribbon in normal blending), two stretched flame sprites on it, a few faint heat-shimmer sprites rising over it (the fake for heat distortion), and `Effects` adds short overlapping tail flames, dark smoke wisps in normal blending that stay in the air behind the path, and embers. `fireballTailScale(range, tail)` shortens the tail on a short throw (a 5 yd throw keeps about 40 %, from 16 yd on it is full; tested). On the hit `Effects` draws a flash, flames flaring outward, saturated ground rings (a normal-blended orange ring under an additive hot one, so they read on light and dark floors), embers, smoke, and what stays on the ground: an orange glow (normal blending under an additive core) over a short-lived dark scorch decal. `Effects` owns ONE `PointLight` created in its constructor and never added or removed (three.js recompiles every lit material when the light count changes): it is moved to the strongest fireball, dimmed to intensity 0 when none flies and flashes on a hit. Pyroblast (`size` 1.7, `heat` 1) is bigger and a darker red, and its cast time grows the ball in the caster's hand (`fireballWindup`), held out to the right of the caster; `windupScale(dist, radius)` caps its apparent size to a share of the screen (`WINDUP_CAP`, tested) and a close camera slides it aside and down, so a close-up never fills the view. Cost: about 25 pooled sprites and two 19-station ribbons per ball plus tail particles under the global `PARTICLE_CAP`, no per-frame allocation (the ribbons rewrite their own vertex arrays), everything handed back when the flight ends. To give another spell the look, add a `fireball(size, heat)` row (any school, but the colours are fire). Without the flipbook file the canvas flame is used. To preview, drive `Effects` with synthetic events from a throwaway page (a test scene, `Effects.update(dt, units)` stepped by hand, `effects.camera` set) and screenshot it.
- Shared fire look (`fireFx.ts`, `FIRE_LOOK` / `fireFieldShape` in `skillVisuals.ts`): every fire skill is built from the same pieces as the Fireball. `FireField` is a persistent field of flipbook tongues (a dark red body in normal blending, a large tongue and a smaller hot one per tongue, each on its own lick cycle and frame phase, tips leaning along the swirl, low broad tongues between the tall ones) round a white-hot core, over an orange glow and a scorch mark: `zone` (Flamestrike: fills the real radius, `fireFieldShape('zone', radius)` keeps every flame inside it, tested; pillar at cast, a jump and ring on every pulse, scorch that builds and stays), `burst` (Scorch, `fireEruption`) and `body` (the burning aura layer, scaled by the unit). The emitters in `effects.ts` are shared too: `fireTongue` (the old `flame()` is now this, so every caller and cosmetic gets the look), `smokeWisps`, `emberShower`, `fireFlash` and `fireGroundGlow` (also used by the fireball hit). Dragon's Breath and Dragon Roar (`fireCone`) add the dark red body, a mouth flash and tongue plus glow patches. A field is about 55 pooled sprites (zone), 30 (Scorch) or 25 (a burning unit) and moves them without allocating; everything is handed back when it ends and the 900 particle cap still applies. Without the flipbook the host's canvas flame is used. Fire forms by ability: `fireball`/`pyroblast` ball, `flamestrike` zone, `scorch` burst, `dragons_breath`/`dragon_roar` cone, aura `burn` body (tested for every fire-school ability).
- `sector(...)`: a flat fan on the ground (any cone).
- Shout pose (`client/src/shoutPose.ts`): a one-shot overlay (lean back with the chest out, then snap forward at `SHOUT_RELEASE`, settle by `SHOUT_DUR`) added on top of the normal pose by all three animators: `RigAnimator` (procedural bones), `ClipAnimator` (applied after the mixer to the canonical bones, `shoutGain`) and the procedural `createCharacter`. `Effects.onShout` -> `Scene.shout` -> `Character.shout()`; the abilities are listed in `SHOUT_ABILITIES`.

## Sample bank (recorded sounds)

All sound is still synthesised (`voices.ts` recipes through `audio.ts`), except what is listed in `client/src/sampleTable.ts`. A table entry is keyed by the id of the sound the engine already plays: `c-<ability>` (released), `cs-<ability>` (wind-up), `hit-<ability>` (lands). When the engine plays that id (`Audio.play`), `SamplePlayer` (`client/src/samples.ts`) takes over from the recipe:

- the file is fetched and decoded the first time it is needed, or just after the audio engine unlocks for entries with `preload: true` (never blocks the menu; it works with the same click-to-unlock as everything else); until it has decoded, or if it is missing or the browser cannot decode it, the recipe plays as before;
- it goes through the same positional `out()` (pan and distance), `sfx` bus, per-id cooldown and global cap (`MAX_SAMPLES` = 8 at once) as the recipes; `volume`, `rate` (1 = as recorded, lower is deeper and longer), `pitchVar`, `volVar`, `powerGain` (follows the hit's power) and `variants` (several takes, one picked at random) are columns of the table; `layer: true` plays the recipe as well (a sample for the body, the recipe for the punch);
- `files` is a list tried in order, so a `.ogg` can come first with an `.mp3` after it.

To add a sample: cut and encode it with ffmpeg (mono, loudness-matched to about -18 LUFS, peak under -2 dB, faded; `ffmpeg -i in.wav -af "pan=mono|c0=0.5*c0+0.5*c1,afade=t=in:d=0.01,loudnorm=I=-18:TP=-2" -ar 44100 -c:a libmp3lame -q:a 4 -map_metadata -1 out.mp3`), keep it under about 60 KB, put it in `client/public/audio/`, add a row to `SAMPLES`, and credit it in `client/src/credits.ts` and `CREDITS.md` (author, source, licence). MP3 is the format every browser decodes, Safari included (Ogg Vorbis and Opus-in-Ogg only decode in recent Safari), so it is the default. The original recording stays out of the repo. `client/test/samples.test.ts` runs the player with a fake `AudioContext` and checks that every file in the table exists and is small. Voice lines can use the same bank (an id per line, `variants` for takes) once their ids are chosen.

## Hosting on Render

The game is built from the GitHub repo `TokeGG/mmoarena` and hosted on Render at https://mmoarena.onrender.com; every push to `main` redeploys it (wait for **Deploy live**, then reload with Ctrl+Shift+R).

1. Push the **contents** of this folder so `package.json` and `render.yaml` sit at the repo root. Leave Render's Root Directory blank and commit `package-lock.json`.
2. Render: **New + > Blueprint**, pick the repo. `render.yaml` sets Node, the Virginia region, the build and start commands and the health check. Or create a Web Service by hand:

| Setting | Value |
|---|---|
| Runtime | Node |
| Region | Virginia |
| Build command | `npm install --include=dev && npm run build` |
| Start command | `npm start` |
| Health check path | `/healthz` |

3. Open the Render URL. One service serves the page and the WebSocket (`wss://<host>/ws`), so there is nothing else to configure and no CORS to set up. The free tier sleeps when idle.

### Environment variables (Render > Environment)

| Variable | Purpose |
|---|---|
| `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` | Free Upstash Redis database so accounts, ratings, history, replays, friends and bot brains survive restarts. (`KV_REST_API_URL` and `KV_REST_API_TOKEN` also work.) Without them everything lives in memory and resets on every restart or redeploy. |

### Running at 62.5 Hz (`ARENA_TICK_MS=16`)

The production blueprint (`render.yaml`) sets `ARENA_TICK_MS` to `16`: the game server then steps the simulation 62.5 times a second instead of 20, so other players are drawn about 35 ms fresher and the server judges positions 3x as finely (NETCODE.md sections 4 and 10 have the numbers). Things to know:

- **Dashboard variables win.** If the Render dashboard already has its own environment variables for the service, a blueprint sync does not add this one: add `ARENA_TICK_MS` = `16` there by hand. To go back to 20 updates a second set it to `50` or remove it (the code default is 50) and redeploy. Players need no action either way; replays record the tick length they were played at.
- **CPU.** The study measured about 1.9x the CPU of 20 Hz (41 -> 78 ms per second of match for a 3v3 with bots, 15 -> 35 ms for a 3v3 of people, 7 -> 18 ms for a 1v1; NETCODE.md 4.3) and the final code measures 2.1x for bot rooms (1v1 20 -> 29, 2v2 27 -> 59, 3v3 37 -> 77 ms of CPU per second of match, NETCODE.md section 10). A Starter instance (0.5 vCPU) holds about 12 1v1 rooms or 6 human 3v3 rooms before the CPU is 70 % busy; the free plan (0.1 vCPU) holds only one or two rooms, so watch the load: `/api/status` -> `tick.load` and the admin panel dashboard ("Server tick"). Above 70 % for 10 seconds the console logs `server busy`; raise the plan or set `ARENA_TICK_MS=50`.
- **Bandwidth.** About 3x the 20 Hz snapshot traffic per player: measured 155 KB/s per client in a 3v3 with the Stage 1 snapshot diet (51 KB/s at 20 Hz), so one 3v3 room sends about 3.3 GB an hour (1.1 GB at 20 Hz).
- **Bots and rotations** were tuned at 20 Hz and are shipped as tuned; their think intervals are in milliseconds and a 40-match bot comparison at 16 ms shows no systematic difference (NETCODE.md section 10).

## Security measures

| Area | Protection |
|---|---|
| Authority | Server-authoritative simulation at a fixed 20 Hz tick; per-viewer snapshot culling; every client message is validated. |
| Accounts | scrypt password hashes, random session tokens in a bearer header (no cookies, so no CSRF), 30-day expiry, rate-limited login and registration. |
| Owner | Founder name plus a secret code entered per session, rate-limited guesses. |
| Avatars | GIF only, checked for size and dimensions on the server and served from a separate path. |
| Replays | Stored compressed with a 30-day expiry and gated by a content hash so a stale replay never plays a wrong fight. |
| Connections | Per-socket message rate limit and message size cap. |
| Storage | All keys sit under one prefix so the database can be shared safely. |

Friend lists live on the account record; who is online is held in memory only, so presence costs no database reads.

## Known limits

- Numbers are tuned with bot duels, not with many humans yet. Retune after you play.
- Matchmaking pairs players in queue order; it does not use rating yet. One rating covers 1v1, 2v2 and 3v3.
- Duels are 1v1 only.
- The procedural character models (`client/src/models.ts`) are only a fallback; every class has a skinned model. Some licences are still to be confirmed (CREDITS.md).

**Arenas and the shared look (0.69.2):** all ten arenas are dressed from one kit (`client/src/arenaKit.ts`, `client/src/arenaMap.ts`). `arenaMap.ts` has one `Theme` per look (`colosseum`, `ruins`, `frost`, `cinder`, `forge`, `sandstone`; `ArenaDef.theme` picks it, gameplay never reads it): sky, fog, one light rig (sun with a shadow box fitted to the bounds, a cool fill, hemisphere light), floor / rampart / cover / deck materials by kit name, the pillar, wall and low-barricade style, torches, banners and the ambient particles (dust, snow or rising embers). - **Kit materials** (`kitMaterial('sandbrick', { repeat })`): a colour map and a normal map (some with a glow map), loaded lazily from `client/public/models/arenas/kit.pak` (`sand`, `sandbrick`, `cobble`, `carved`, `sandstone`, `obeliskstone` from the "Arena" scene; `snow`, `ice`, `frostbrick`, `mossbrick`, `flagstone`, `planks`, `dirt` generated by `scripts/lib/texgen.mjs`) and from the arena's own pack (hell textures). A plain canvas texture stands in until the pack arrives, and stays if it cannot be loaded, so the arena always works; the main menu never waits for a pack (an arena's pack is fetched when that arena is first shown or previewed). Materials that tile by world size use `worldBox(w, h, d, tile)`, which scales the UVs.
- **Scanned pieces and terrain:** `sandstone.pak` (stadium `shell_*`, `prop_obelisk_N`) and the `forge.pak` grate replace the built-in dressing once loaded (`ArenaEnvironment.ready` resolves then). The shell pieces `shell_Object_19/21/29` (leaning posts and beams) are hidden while the camera is above 13 yards (`update(t, camera)`). Cinder and forge packs carry only textures and are otherwise generated by the client: `ringTerrain` (arenaKit.ts) builds ONE welded skin of terrain round the rampart out to the horizon (rounded-rectangle offset rings lifted by a height function: crater wall, lip, basalt plain and lava sea with islands for cinder; ledge, lava moat and cliffs for forge), with vertex colours for heat, glowing veins as an additive second layer (`emissiveFromVertexColor`), a lava-sea disc, instanced boulders, a sky dome (`skyDome`, horizon glow at the horizon) and the far ridges; cinder's pillars are generated obsidian horns (`hornGeometry`, UVs in yards, no stretching). `Theme.zone` is the opacity of the blue/red start-zone tint (small on dark lava floors). Crates and wall blocks are baked into two meshes per map (`BoxBatch`).
- **Making the packs:** `node scripts/prep-arena.mjs --hell1 <hell_arena_1.glb> --hell2 <hell_arena.glb> --arena <arena.glb> [--only kit|cinder|forge|sandstone] [--preview dir]`, then `npx tsx scripts/pack-models.ts`. The originals are not kept in the repo.
- **Adding an arena from a GLB:** (1) add the layout to `arenas.json` (bounds, mirrored `pillars` / `walls` / `lows` / `deck`, `spawns`, `gateX`, `nav` points; keep spawn-to-spawn sight broken and all spawn and route points free); (2) add a `Theme` (reuse kit materials; for a scanned look add a prep step in `scripts/prep-arena.mjs` producing a pack of named nodes and a `pack` id on the theme, with a case in the pack-loading block of `buildArenaEnvironment`); (3) credit the model in `client/src/credits.ts` and `CREDITS.md`; (4) bump `SIM_REVISION`, run `npx tsx scripts/gen-wiki.ts` and the tests (`shared/test/arenaMaps.test.ts` runs bots on every arena, `client/test/arenaPacks.test.ts` checks the packs and credits).
- **Cover: what you see is what blocks (0.69.4):** the sim blocks with a vertical circle per pillar (`x, z, r`) and a box per wall and low, the same at every height a player sees (0 to about 2.2 yards, chest 1.4), so the drawn piece must have that footprint. `client/src/cover.ts` builds every pillar, wall and low as a list of parts (`pillarParts`, `wallParts`, `lowParts`; `arenaMap.ts` only bakes them, one mesh per material) and is the one place to change a look. Rules: a pillar is a round (or finely faceted: 12+ sides) shaft of radius exactly `r` up to `COVER_FLAT` (2.6 yards; `taperedShaft`, `spireGeometry`, `hornGeometry` in `arenaKit.ts` keep it); taper, flare, lean, ridges at full depth and ornaments only start above 2.5 yards; trim at head height may stand at most 0.04 outside it, ridges cut at most 0.03 inward; a wall or low has its faces on the rect (0.05 of trim at most) and its ornaments inside it. Things that must not claim to block are `decal` parts (flat rings on the floor: moss, snow, embers) or `debris` parts (stones under 0.6 yards high lying wholly outside the shape). Never draw a square pillar on a circle: sandstone's obelisks are a round carved pedestal 2.6 yards high with the (square, scanned) obelisk standing on it above head height. `npx tsx scripts/audit-cover.ts` slices the same parts at 0.1 / 0.5 / 1.0 / 1.4 / 2.0 / 2.5 yards and prints, per arena, the worst over- and under-reach against the collision shape (`--rows` for every measurement; exit code 1 on a problem); `client/test/cover.test.ts` runs it for all ten arenas, and also checks that the sim's sight line (`hasLOS`) starts where the drawn outline ends (allowing the `LOS_PEEK` slide). When you add or restyle cover, run the audit; to change the footprint itself, change `arenas.json` (and bump `SIM_REVISION`), not just the model.
- **Budgets:** about 1500 draw calls and 300k triangles per arena, textures at most 2048 px (the kit uses 1024), anisotropy 4; repeated props are instanced or merged. `ArenaEnvironment.stats()` counts the scenery's meshes and triangles.
